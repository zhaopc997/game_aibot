### 2.3 依赖编排

`docker-compose.yml` 仅 4 个服务：PostgreSQL 16 / Redis 7 / Elasticsearch 8.13.4 / MinIO。

**但三处关键不一致**（已复核）：

| 服务 | compose 映射 | `application.yml` 默认值 | 结果 |
|---|---|---|---|
| PostgreSQL | `5432:5432` | `localhost:5433` | ❌ 连不上 |

## 三、功能设计

### 3.1 AI 能力设计（文档意图 vs 代码实现）

设计意图（`docs/architecture/architecture-v2.md`，810 行，质量较高）是 **Plan-and-Execute Agent**：

```
用户提问 → Planner(LLM 生成 plan JSON) → Executor(按序调 Tool) → Reflect(判定重试/完成) → 回答
```

实际实现（`AgentService.java`，9,249 字节）：

```
用户提问 → 硬编码 step1: search_guides(写死) → 硬编码 step2: check_compatibility(恒返回 COMPATIBLE)
        → step3: LLM 综合 → 回答
```

**已复核证据**：
- 全仓 `grep "Planner|StateGraph|Reflect"` → **零命中**，无任何 Planner/Reflect 实现
- `AgentService.java:77/102` 工具名与参数为**字面量写死**，LLM 无选择权
- `OpenAiLlmClient` 请求体只有 `model/messages/temperature/max_tokens`，**无 `tools` 字段** → function-calling 从未接通
- `AgentService.java:135` 真实调用 `llmClient.chat(...)`，但类注释 `:24` 仍写"不接真 LLM，固定跑两步"→ **注释已过期且误导**

### 3.2 RAG 设计

| 环节 | 文档设计 | 代码实现 | 判定 |
|---|---|---|---|
| 切分 | Chunk 500 字 + 50 overlap，按 step 切 | **1 篇攻略 = 1 chunk**，且 step 的 `description` 全文被丢弃（`IndexerService.java:170-173` 只取 title） | ❌ 未实现 |
| 嵌入 | 本地 bge-m3，**768 维** | 云端 SiliconFlow，**1024 维** | ❌ 方案与数值均不同 |
| 召回 | BM25 Top-50 + KNN Top-50 | `topK=5` | ❌ 差 10 倍 |
| 融合 | **标准 RRF**（1/(k+rank) 加权） | `mergeUnique()` 纯去重拼接（`HybridRetriever.java:197-207`，已复核无 rank 公式） | ❌ 名为 RRF 实为去重 |
| 精排 | BGE Reranker Top-10 | `grep rerank` **零命中** | ❌ 未实现 |
| 版本过滤 | 强制 `{game_id, version_id:[current,±1]}` | 仅 `term gameId`，`RagQuery.versionId` 定义了但从未被读取 | ❌ 未落地 |
| 降级 | PG tsvector 兜底 | **仓库无任何 tsvector/全文检索**，PG 侧用 `LOWER(title) LIKE '%kw%'` | ❌ 降级链路不存在 |

**关键缺陷**：BM25 请求 size 就是 topK（`HybridRetriever.java:95`），而融合是「BM25 优先 + KNN 补缺」，因此 **KNN 向量检索在实践中几乎永远不生效**——向量白建、embedding 白算。

**结论**：RAG 是全项目**最真实的模块**（ES 写入/检索/事件驱动增量/重建 API 都真实可用），但检索质量控制手段（切分、精排、融合）三项全缺，召回质量会明显低于文档预期。

### 3.3 Tool 框架

机制层面**设计正确且闭环**：注解注册（`ContextRefreshedEvent` + 反射扫描）→ 参数解析（`@ToolParam` 名优先）→ 类型转换 → `ToolResult` 封装（带耗时）。

但只有 5 个工具，且质量参差：

| 工具 | 实现性质 | 证据 |
|---|---|---|
| `search_guides` | 🟢 真实 | 走 ES 混合检索 |
| `check_compatibility` | 🔴 **假实现** | `GuideSearchTools.java:58-65` **不查任何数据库**，无论什么攻略恒返回 `COMPATIBLE`，注释自承"mock 阶段一律视为兼容" |
| `get_game_map` | 🔴 假数据 | 硬编码 marker 101/102 + 编造坐标，而 `InteractiveMap` 表真实数据存在却不用 |
| `simulate_build` | 🔴 硬编码 | 三个角色的成长曲线内联为数学公式，注释称"依据真值库"，但 `game_character`/`game_weapon` 真值表**未接入** |
| `get_wiki_entry` | 🟡 半真半假 | 先查 DB，查不到则编造"官方资料词条"兜底 |

另有两个机制缺陷：`resolveArgs` **不校验 `required`**（`ToolRegistry.java:100` 只写进 `ParamSpec` 供人看），`List` 参数**不做元素类型转换**（`:185` 直接透传）——一旦 LLM 传 `List<Integer>` 而方法签名是 `List<Long>`，反射调用必崩。当前只因 `AgentService:93` 恰好传 `List<Long>` 而侥幸成功。

### 3.4 Memory 设计

设计意图是三层记忆（Short→Redis，Long→PG JSONB），实际：

- `InMemoryMemoryService` 是两个 `ConcurrentHashMap`，**进程重启全部丢失**；类注释自认"骨架阶段全部 mock"
- `readShort()` **全项目零调用方** → AgentService 只写不读，**多轮对话完全无上下文**
- `savePreference()` **零调用方** → `loadPreference()` 恒返回空对象 → **个性化链路整条断开**
- `pom.xml` 已引入 redis starter、`application.yml` 已配 redis，但 memory 模块 `grep Redis` 零命中 → **依赖就位代码没写**

### 3.5 社区与内容设计

这部分**设计质量最高、完成度最好**：多态点赞/收藏/评论（`target_type + target_id`）、问题悬赏与采纳、审核队列（`PENDING/PASSED/REJECTED/NEED_HUMAN` + 风险分级）、攻略 7 态状态机（`DRAFT/PENDING_REVIEW/PUBLISHED/PENDING_VERIFICATION/OUTDATED/ARCHIVED/REJECTED`）、版本快照 + diff + 克隆。这些是真实的产品级设计，不是骨架。

### 4.2 页面逻辑要点

**GameDetailPage（500 行，最重页面）**：8 个 Tab（攻略/角色/武器/圣遗物/机制/资讯/百科/讨论），首屏 `Promise.all` **并发 9 个请求**，其中角色/武器/圣遗物/机制四个接口 `size` 参数达 300/400/100。无数据缓存层 → 用户只看"攻略"Tab 时，另外 4 个大接口的数据已全部下载解析进内存。同时内置 **31 款游戏**的 `FALLBACK_GAMES_MAP` 兜底，对每个请求 `.catch(() => null)` 吞错——若游戏 id 不在 map 中（如 id 32+）且接口 404，页面显示"游戏不存在"而非真实错误。

**AIChatPage（220 行）**：**明确关闭流式**（`stream: false`），无 SSE、无打字机，占位是 3 点 bounce 动画。回答用 `whitespace-pre-wrap` 纯文本渲染，**不解析 Markdown**。且未复用统一的 `unwrap()`，直接读 `res.data?.data`，业务错误码（`code != 0`）会被静默吞掉并落到兜底文案。亮点是 `<details>` 折叠 plan 步骤 + sources 跳转 + `crypto.randomUUID()` 会话 ID。

**GuideEditorPage（167 行）**：裸 `<textarea>`，placeholder 承诺 Markdown 但**无编辑器库、无预览**；提交时把整篇内容压成**单个 `step_id: 1`**，层级全丢；`difficulty`/`type` 硬编码，UI 无法选择。

**前端状态管理**：仅 Context（AuthContext 86 行）+ 页面本地 useState，**无 React Query/SWR**。token 存 localStorage（XSS 可窃取）。`AuthContext.tsx:43` 的 `react-hooks/exhaustive-deps` 依赖 lint 被 eslint-disable 绕过。

**组件层**：`components/ui/` 7 个自研基础组件（285 行，质量规范，forwardRef/displayName 齐备），`components/stats/` 2,330 行。`package.json` 装了 8 个 Radix 包，**实际只用了 `@radix-ui/react-slot` 一个**，dialog/popover/tooltip/tabs 等全装未用——`CharacterDetailModal` 手写遮罩弹窗，缺焦点陷阱/Esc/aria-modal。

## 七、一句话结论

> **架构骨架（模块划分、技术选型、表设计）质量高于平均水线，RAG 检索、社区审核、数值体系三块已达生产可用；但"AI Native Copilot"的核心——Agent 智能链路（Planner/ToolCalling/Memory/降级）、数据采集工程化、前端 43% 页面——仍停在骨架与 mock 阶段，且存在"假数据伪装成真实功能"（`check_compatibility` 恒真、`simulate_build` 硬编码、7 处静默兜底）、"文档承诺与代码实现大面积不一致"（5 张 AI 表未建、5 个验收 Case 3 个确定失败）、"环境配置不可用"（端口三处错位）三类问题。**
>
> **建议优先顺序**：先修 6 个 P0（尤其端口与 401 并发锁，这两个直接决定项目能否启动和能否稳定使用）→ 再补 P1 中 7–13（让 Agent 链路和 RAG 真正名副其实）→ 最后按 P2 清理文档债与技术债。
